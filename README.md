# ts-narrowing-matrix

Which TypeScript declaration forms keep a narrowed type, measured across
compiler versions.

```ts
const el = document.getElementById('x'); // HTMLElement | null

if (el) {
  function decl() { el.id; }          // error TS18047: 'el' is possibly 'null'
  const arrow = () => { el.id; };     // fine
}
```

Same binding, same guard, same block, one character of difference in how the
consuming function is written. **The table below is generated by compiling the
fixtures in `cases/` under each pinned TypeScript version** — nothing in it is
typed by hand.

## What it shows

**1 · The hoisted `function` declaration is the only form that fails
everywhere.** Every other row depends on what is being narrowed or which
compiler is reading it. A `function` declaration loses the narrowing for a
`const`, for a `let`, for a parameter, at module scope, inside a function body,
in every version tested.

A `function` declaration is hoisted to the top of its enclosing block. Where the
compiler analyses its body, control flow has not passed through the `if` yet —
so there is no narrowing to inherit. Writing the same function as `const f =
() => {}` or `const f = function () {}` creates it at the position it is
written, after the guard.

**2 · TypeScript 5.4's "Preserved Narrowing in Closures" is narrower than it
reads.** The release notes say:

> When parameters and `let` variables are used in **non-hoisted** functions, the
> type-checker will look for a last assignment point.

Measured, 5.4 moved exactly one row in this matrix: a **function-scope** `let`
consumed by an arrow. A **module-scope** `let` still loses the narrowing in
every closure form, in the current release. The word "non-hoisted" is in the
notes; the scope restriction is not.

**3 · A parameter is not a `let`.** A parameter narrowed by a guard keeps its
narrowing in an arrow function, and always has — including in versions before
5.4. A module-scope `let` never does.

## Why this exists

The answer is documented — `microsoft/TypeScript`
[#42694](https://github.com/microsoft/TypeScript/issues/42694), *"Function
expression / Function declaration different behavior when narrowing types"*,
opened February 2021 and closed. It is not *findable*: the TypeScript handbook's
[Narrowing chapter](https://www.typescriptlang.org/docs/handbook/2/narrowing.html)
is ~29,000 characters and does not contain the word "hoist".

This repository is the measurement rather than the explanation — the table is
what a build actually does, re-run in CI so it stays true when the compiler
changes.

## Running it

```bash
node scripts/run-matrix.mjs          # run the matrix, rewrite the table above
node scripts/run-matrix.mjs --check  # fail if the table is out of date
```

No dependencies. Each version is fetched by `npx` at run time, so the first run
is slow and nothing is vendored.

Adding a case means adding a line to a file in `cases/` and a label for its line
number in `CASES` at the top of `scripts/run-matrix.mjs`. **Line numbers are the
case identity**, so inserting a line above an existing case relabels it — the
script has no way to detect that, and it is the one thing to be careful about.
